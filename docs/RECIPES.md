# FastVLM CoreAI — Compression Recipes

Compression reduces model size and (for symmetric schemes) improves GPU throughput
by reducing memory bandwidth pressure. This document covers the compression preset
system, YAML recipes, and the scanner pipeline for generating per-model recipes.

---

## Compression presets

Three named presets, matching Apple's `coreai.llm.export --compression` options:

| Preset | Scheme | 1.5B tok/sec | 1.5B memory | Use when |
|--------|--------|-------------|-------------|---------|
| `none` | fp16 (no compression) | 59 | 7.0GB | Maximum quality |
| `8bit` | int8 symmetric_with_clipping per_block_32 | 71 | 2.8GB | Quality-first compression |
| `4bit` | int4 symmetric_with_clipping per_block_32 | 115 | 2.0GB | Best overall (recommended) |

```bash
# Named preset
python scripts/export_fastvlm.py --variant 1.5b --compression 4bit
python scripts/export_fastvlm.py --variant 1.5b --compression 8bit

# No compression (fp16)
python scripts/export_fastvlm.py --variant 1.5b
```

**Key finding:** `4bit` (per_block_32 symmetric) and the former `4bit_per_channel`
(per_channel symmetric) produce identical throughput on M4 Pro GPU. The original
7.2 tok/sec regression was caused by **asymmetric** quantization (from Apple's MLX
checkpoints), not per_block vs per_channel. Both symmetric schemes are fast.

**Recommended defaults:**
- **0.5B**: `none` (fp16) — already small, no compression needed
- **1.5B**: `4bit` — 115 tok/sec, 2.0GB, clean output
- **7B**: `4bit` — 50 tok/sec, 5.9GB, the only viable option (fp16 = 29GB)

## YAML recipes

For per-layer mixed precision — some layers at int8, some at int4, sensitive layers
at fp16. Use `--compression-config` instead of `--compression`:

```bash
# Use a pre-built recipe
python scripts/export_fastvlm.py --variant 1.5b \
    --compression-config quantization_recipes/fastvlm-1.5b-aggressive.yaml

# --compression and --compression-config are mutually exclusive
```

`--compression` and `--compression-config` are mutually exclusive.

### Pre-built recipes in `quantization_recipes/`

| Recipe | Description |
|--------|-------------|
| `fastvlm-{variant}-aggressive.yaml` | Base int4, int8 for moderately sensitive layers, fp16 for critical layers. Generated by scanner. |
| `fastvlm-{variant}-conservative.yaml` | Base int8, fp16 for sensitive layers. Higher quality, larger size. |

## Generating recipes with the scanner

`scan_quantization_sensitivity.py` measures per-layer quantization sensitivity and
produces YAML recipes calibrated to the model's actual weight distribution.

### How it works

For each quantizable `nn.Linear` layer, the scanner measures two things:

**1. Local sensitivity** (always computed, ~1ms per layer):
Frobenius norm ratio of the weight perturbation under fake quantization.
`||W - W_quant|| / ||W||` — how much the weight matrix changes under quantization.

**2. KL divergence** (optional, requires corpus fixtures, ~3s per layer for 0.5B):
Temporarily quantizes the layer, runs the decoder on the 9-image corpus using
pre-built fixtures from `fastvlm_fixtures.py`, measures KL divergence between
the reference and quantized final-position logit distributions. Decoder-only
inference — no vision encoder needed per layer.

The scanner then uses percentile-based thresholds (not hardcoded values) to assign
each layer to fp16/int8/int4 based on the observed sensitivity distribution.

### Usage

```bash
# Fast — local sensitivity only, no fixtures needed (~1s)
python scripts/scan_quantization_sensitivity.py --variant 0.5b --local-only

# Full — local + KL on corpus fixtures (~8min for 0.5B, longer for 1.5B/7B)
python scripts/build_fixtures.py --variant 0.5b   # one-time
python scripts/scan_quantization_sensitivity.py --variant 0.5b

# Control sensitivity thresholds (lower = more fp16 = safer)
python scripts/scan_quantization_sensitivity.py --variant 1.5b \
    --critical-percentile 85 --sensitive-percentile 65
```

**`--local-only` is sufficient when:**
- The model's KL sensitivity is uniformly low (0.5B — all layers score ~0.0000)
- You want a quick recipe for initial testing
- Fixtures haven't been built yet

**Full KL is worth running when:**
- Model is 1.5B or 7B (larger models have more inter-layer sensitivity variation)
- You want the most accurate recipe for the final export

### Interpreting the output

```
Sensitivity distribution (169 scannable layers):
  min=0.0053  median=0.0056  max=0.0074  stdev=0.0003
  p90=0.0060  p70=0.0057
  largest gap=0.00052  elbow=0.0074
  ⚠ No clear elbow — scores are uniformly distributed.
```

**Distribution stats:**
- `stdev` — low stdev (like 0.5B's 0.0003) means all layers are similarly sensitive.
  Mixed recipes add little value over uniform 4bit in this case.
- `largest gap` — the biggest jump between consecutive sorted scores. A large gap
  indicates a clear elbow — layers above the gap are genuinely more sensitive.
- `elbow` — the sensitivity value at the largest gap. Layers above this are
  candidates for fp16 protection.
- `⚠ No clear elbow` — scores are uniformly distributed. Percentile-based
  thresholds are the best available heuristic, but the distribution doesn't
  naturally separate into "sensitive" and "robust" groups.

**Layer table:**
```
Layer                                        Params    Local      KL    Conserv   Aggress
lm_head.weight                            77,791,232   1.0000   1.0000      fp16      fp16
layers.0.self_attn.q_proj.weight             802,816   0.0068   0.0001      fp16      fp16
layers.23.mlp.up_proj.weight               4,358,144   0.0063   0.0000      int8      int8
layers.12.self_attn.v_proj.weight            802,816   0.0057   0.0000      int8      int4
```

- Layers with `local >= p90` → fp16 in both recipes
- Layers with `p70 <= local < p90` → int8 in aggressive recipe
- Layers below `p70` → int4 in aggressive recipe (int8 in conservative)
- `lm_head` and norms are always fp16 (regardless of sensitivity)

### Known results by variant

| Variant | Local stdev | KL stdev | Elbow | Recommendation |
|---------|-------------|----------|-------|----------------|
| 0.5B | 0.0003 (very flat) | ~0.0000 | None | Uniform 4bit is optimal |
| 1.5B | TBD | TBD | TBD | Run full scan |
| 7B | TBD | TBD | TBD | Run full scan |

0.5B result: 1 fp16 (lm_head), 168 int4 for aggressive — essentially uniform 4bit.
This confirms the named `4bit` preset is already optimal for 0.5B.

## Verifying a recipe before export

Always run `verify_decoder.py` Phase 4 before exporting a new recipe.
See [docs/VERIFICATION.md](VERIFICATION.md) for the full guide.

```bash
# Verify a scanner-generated recipe
python scripts/verify_decoder.py --variant 1.5b \
    --compression-config quantization_recipes/fastvlm-1.5b-aggressive.yaml

# Verify a named preset
python scripts/verify_decoder.py --variant 7b --compression 4bit
```

Phase 4 evaluates the recipe over the 9-image corpus and recommends
EXPORT or CAUTION based on top-5 overlap at the final generation position.

## YAML recipe format

Recipes use `QuantizerConfig` native format, loadable by `load_compression_config()`:

```yaml
# Generated by: scan_quantization_sensitivity.py
# Recipe type:  aggressive
# Variant:      fastvlm-1.5b
# Summary:      {'fp16': 18, 'int8': 34, 'int4': 117}
#
quantization_config:
  execution_mode: eager
  global_config: null
  module_type_configs:
    torch.nn.modules.linear.Linear:
      op_state_spec:
        weight:
          dtype: int4
          qscheme: symmetric_with_clipping
          granularity:
            type: per_block
            block_size: 32
            axis: 1
      op_input_spec: null
      op_output_spec: null
    coreai_torch.composite_ops.SDPA: null
    coreai_torch.composite_ops.RoPE: null
    coreai_torch.composite_ops.RMSNormImpl: null
    fastvlm_decoder.FastVLMRMSNorm: null
  module_name_configs:
    # Per-layer overrides for sensitive layers
    lm_head:
      op_state_spec:
        weight:
          dtype: fp16
    layers.0.self_attn.q_proj:
      op_state_spec:
        weight:
          dtype: int8
          qscheme: symmetric_with_clipping
          granularity:
            type: per_block
            block_size: 32
            axis: 1
    # ... more overrides
```

**Key fields:**
- `module_type_configs`: base compression for all `nn.Linear` weights
- `module_name_configs`: per-layer overrides (scanner output)
- `fastvlm_decoder.FastVLMRMSNorm: null`: excluded — 1D weight incompatible with per_block axis=1
- Setting a layer to `null` excludes it from compression (keeps fp16)

---

## Why Apple's 4bit preset structure

Apple's `coreai.llm.export --compression 4bit` uses `global_config` to apply compression
to all modules, with `module_type_configs` for exclusions. Our presets use
`module_type_configs` targeting `torch.nn.modules.linear.Linear` only, because
`global_config` hits `FastVLMRMSNorm` (a custom module with a 1D weight) and causes
`"axis 1 out of bounds for rank 1 tensor"`. The weight spec on `nn.Linear` is
identical to Apple's — only the targeting approach differs.
